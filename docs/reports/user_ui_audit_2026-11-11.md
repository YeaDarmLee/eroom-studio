# 사용자 화면 UI 점검 — 2026-11-11

서로 독립적인 두 보조 에이전트의 디자인/기술 평가와 부모 에이전트의 로컬 브라우저 검증을 종합했다. 관리자 UI는 제외했으며 제품 코드는 변경하지 않았다.

## 결론

휑해 보이는 주원인은 고정 높이 이미지 영역, 반복되는 큰 세로 간격, 실제 지점/방 정보가 늦게 나오는 순서다. 읽기 어려운 주원인은 10–12px 레이블과 낮은 대비다. 장식 추가보다 정보 배치와 가독성 정리가 먼저다.

## 확인 범위와 한계

- 코드: 공통 base, public 및 user 템플릿. 소개·가입·온보딩·빈 상태 등은 소스 검토.
- 실제 브라우저: 로컬 SQLite 미리보기의 홈, 지점 상세, 로그인, 계약이 있는 마이페이지, 방 상세 및 계약 불가 안내. 기본 화면과 390×844 모바일 확인.
- 운영 DB·실제 고객 계정·계약 제출은 사용하지 않았다. 기존 로컬 테스트 DB에 있던 계약 상태를 그대로 관찰했다.
- 실제 사진이 등록된 운영 화면 전체나 모든 기기, 전체 키보드 계약 흐름은 검증하지 않았다. 사진 없음은 조건부 상태로 평가했다.

## 우선 문제

1. **P1 — 모바일 고정 공실 카드가 본문을 가린다.** 홈 `index.html:165`의 fixed 카드가 모바일에서도 160px 폭으로 유지되며 닫기 기능이 없다. 390px 뷰포트에서 본문 위 겹침을 확인했다. 인라인 공실 요약 또는 접을 수 있는 작은 진입점으로 바꾼다. 관련 방향: adapt/layout.
2. **P1 — 핵심 정보와 버튼의 색상 대비가 낮다.** `base.html:136–145`의 gray-400 #CBD5E0, gray-500 #A0AEC0, gray-600 #718096은 흰색 대비 각각 약 1.49/2.26/4.02:1. primary #F39C12와 흰색 대비는 약 2.19:1이다. 이는 불투명 단색 조합의 계산값이며 모든 픽셀의 실측값은 아니다. `dashboard.html:136,144,159,168` 레이블은 모바일 10px/PC 11px에 gray-400을 적용한다. 마이페이지에서 실제로 연하고 작은 레이블을 확인했다. 주요 라벨 13–14px 이상과 충분한 대비를 우선 적용한다. 관련 방향: typeset/colorize.
3. **P2 — 이미지가 없는데도 큰 이미지 자리를 유지한다.** `room_detail.html:23,37`의 4:3 영역은 사진이 없는 로컬 방 상세에서 첫 화면 대부분을 차지했다. 이름·가격이 아래로 밀린다. 지점 상세 `branch_detail.html:100`은 480px 슬라이더를 유지하며 실제 사진이 없으면 외부 일반 스튜디오 이미지를 사용한다. 사진 없음/로드 실패 시 공간을 축소하고 가격·면적·시설 요약을 올린다. 관련 방향: layout/harden.
4. **P2 — 모바일에도 PC 수준 여백이 반복되고 지점 안내가 늦게 나온다.** `index.html:5` hero 680px, `:22` 혜택 상하 96px, `:58,95` 절차/지점 상하 112px, `:60,97` 제목 아래 80px. 실제 모바일 DOM에서 지점 섹션 시작이 문서 상단 약 2156px 지점이었다. 지점·공실 정보를 앞당기고 모바일 간격을 줄인다. 관련 방향: layout/adapt.
5. **P2 — 빈 상태와 신청 흐름의 다음 행동이 약하다.** `dashboard.html:487` 계약 없음은 큰 빈 카드와 홈 이동만 제공한다. 기존 계약 연결이 필요한 사용자에게 다음 행동을 구분하지 않는다. `branch_detail.html:270` 만실 상태도 대체 지점/문의 연결이 약하다. `room_detail.html:243` 신청하기는 룸 정보와 동급 탭이며, 신청 폼은 여러 결정 항목이 길게 이어진다. 신규 탐색/기존 계약 연결/만실을 구분하고 방 핵심 조건과 다음 행동을 모은다. 관련 방향: onboard/clarify/layout.

## 추가 기술 사항

- P1: `public_floor_plan_component.html:380` 방 선택이 클릭 가능한 div로 구현되어 링크/버튼 의미와 키보드 동작이 없다. 방 상세로 가는 링크로 구현해야 한다.
- P1: `dashboard.html:531–545,570–588` 프로필/비밀번호 label과 input에 for/id 연결이 없다.
- P2: 도면 최소 너비 560px, 모바일 방 라벨 약 9.6px. 도면과 함께 읽기 쉬운 방 목록이 필요하다.
- P2: 모바일 메뉴 토글에 aria-expanded/aria-controls와 충분한 터치 영역이 없다. 이름은 dialogs.js가 주입하므로 이름 누락으로 판정하지 않았다.
- P2: 고정 헤더 80px와 main 상단 여백 64px가 다르다. 앵커에는 scroll-margin이 없다. 실제 앵커 최종 가림은 별도 검증 대상이다.
- 온보딩의 영어/indigo 스타일, 로그인·가입의 버튼 규칙이 통일되지 않았다. 소개의 시간제 이용 문구와 지점의 숨겨진 시간제 탭은 제품 의도 확인이 필요하다.

## 좋은 점

- 가격·보증금·입주일·계약 상태와 접수 후 안내가 이미 있어 정보를 다시 만들 필요가 적다.
- 로그인 로딩/오류, 원래 방으로 복귀하는 경로, 지점으로 돌아가는 링크가 있다.
- dialogs.js에는 모달 포커스 이동·Tab 순환·Escape·포커스 복귀가 구현돼 있다. 템플릿 속성만 보고 누락으로 단정하지 않았다.

## 이용자 관점

- 첫 방문자: 실제 지점/가격 비교 전 소개 영역을 오래 지나야 한다.
- 모바일 이용자: 고정 보조 카드가 본문과 경쟁하고 마이페이지 뒤쪽 탭은 가로 이동이 필요하다.
- 저시력/키보드 이용자: 낮은 대비, 작은 글자, 도면의 클릭 전용 방 선택이 부담이다.
- 기존 입주자: 계약 없음 상태에서 계약 연결과 신규 탐색이 구분되지 않는다.

## 휴리스틱 잠정 평가

소스와 제한된 로컬 흐름에 대한 평가이며 제품 완성도 측정치가 아니다. 4점이 가장 좋다.

| 항목 | 점수 | 근거 |
|---|---:|---|
| 상태 표시 | 3 | 로딩·계약 상태·접수 안내 |
| 현실 언어 | 2 | 가격 정보 명확, 영어 온보딩 혼재 |
| 사용자 통제 | 2 | 뒤로가기 있음, 공실 카드 접기 없음 |
| 일관성 | 2 | 공통 서체, 인증 화면 시각 규칙 차이 |
| 오류 예방 | 2 | 필수/동의 있음, 모든 오류 경로 미검증 |
| 인지 용이성 | 2 | 계약 요약 있음, 레이블 가독성 낮음 |
| 효율 | 2 | 탭/지점 전환 있음, 비교 정보 도달이 늦음 |
| 심미성과 집중 | 2 | 큰 빈 영역과 보조 카드 비중 과다 |
| 오류 복구 | n/a | 실패·입력 보존 흐름 미검증 |
| 도움말 | 2 | 절차/문의 있으나 상황별 다음 행동 약함 |

잠정 19/36. 오류 복구는 부적용이 아니라 이번 점검의 미검증 항목으로 합산에서 제외했다. 이전 점검과 비교 가능한 제품 점수로 사용하지 않는다.

## 자동 점검

명령: `impeccable.cmd detect --json app/templates/public app/templates/user app/templates/base.html`.

종료코드 1, 경고 8건. 대비 2건은 지점 상태 배지의 2.6:1/2.0:1 경고로 수동 색상 평가와 같은 계열이다. 이미지 경고 3건은 Alpine :src 바인딩 존재를 확인하여 누락 확정에서 제외했다. 캔버스 패딩 1건, 의미 있는 보라색 사용 1건, 실제 text-xl을 반영하지 않은 제목 계층 1건도 결함 확정에서 제외했다. 자동 경고 수를 확정 결함 수로 사용하지 않았다.

## 권장 순서와 후속 선택

모바일 가림 → 글자 크기/대비 → 빈 이미지와 홈 정보 순서 → 계약 신청·빈 상태 → 화면 간 일관성 순서로 개선한다. 마지막에 실제 데이터·모바일·키보드 동선을 함께 확인한다.

다음 선택은 ① 홈/지점 탐색과 마이페이지 중 어디부터 개선할지, ② 기존 스타일을 유지하며 핵심 문제만 고칠지 사용자 화면 전체를 정돈할지다.

## 후속: 메인 화면(`/`) 집중 점검

사용자가 개선 우선 대상을 메인으로 지정했다. 아래는 앞선 PC/모바일 렌더링과 현재 index.html/base.html/Branch 모델 재검토를 종합한 내용이며 새로 화면을 실행한 결과는 아니다.

### 첫 화면

- 메인 hero는 지점 사진 데이터가 아닌 외부 readdy.ai 이미지 URL을 직접 사용한다. 실제 지점의 시설·분위기를 보증하는 사진으로 취급해서는 안 된다. 실제 지점 사진 중심으로 구성하는 편이 공간 선택에 유용하다.
- 모바일 제목은 기본 48px이고 강제 줄바꿈까지 있어 좁은 화면에서 문장이 잘게 끊긴다. 큰 사진·제목에 비해 사용자가 바로 판단할 지역/지점·공실·가격 요약이 없다.
- hero 내부 컨테이너는 max-w-7xl만 있고 w-full이 없다. 바깥은 flex이므로 공통 헤더/아래 섹션과 동일한 폭·왼쪽 정렬선을 보장하지 않는다. 앞선 기본 화면에서도 본문 문구가 중앙 쪽에 배치됐다. 전체 화면 폭을 기준으로 동일한 콘텐츠 정렬선을 적용할 필요가 있다.
- 사진 위 연한 보조 문구와 흰색/주황 CTA는 대비를 높여야 한다. 사진의 밝기에 의존하는 가독성은 피한다.

### 정보 순서와 지점 비교

- 현재 순서: 큰 소개 → 혜택 4개 → 이용절차 4단계 → 지점 안내. 목적지가 지점/방 선택인 방문자는 설명 영역을 두 번 지나간다.
- 지점 카드에는 주소·설명·24시간·전체 층수·전체 방 수가 있지만, 월간 공실 수와 가격 범위는 없다. 공실은 별도 고정 카드로 떨어져 있어 카드만 보고 비교하기 어렵다.
- 전체 층수/전체 방 수보다 사용자가 선택에 필요한 위치·이용 가능한 방·월 요금·입주 가능 시점이 우선이다. 가격 범위를 추가한다면 실제 조건에 맞는 데이터로 계산하고 월간/시간제 상품을 구분해야 한다.
- available_rooms_count는 status=available인 monthly 방만 센다. 현재 공실 수와 퇴거 예정 사전 예약 가능 방은 다른 의미이므로 합치거나 '예약 가능 전체'로 이름을 바꾸지 않는다. 표시 기준부터 명확하게 해야 한다.
- 카드 주소는 12px gray-500, 설명은 12px gray-400 italic과 두 줄 자르기다. 구분 정보가 작고 옅게 처리돼 지점명/사진 외에는 눈에 남기 어렵다.

### 보조 콘텐츠와 신뢰

- 혜택의 '기본 규정'은 선택 이유보다 이용 안내에 가깝다. 혜택 영역은 실제 검증된 방음/시설/입지 등 차별점을 담거나 간결한 이용 정보로 축소하는 편이 적절하다. 새로운 장점·보장 문구는 사실 확인 없이 추가하지 않는다.
- '24시간 이용'과 '24시간 고객 지원'은 다른 주장이다. 실제 상담 운영시간 확인이 필요하며 동일한 의미로 제시하면 안 된다.
- footer의 이용 안내/자주 묻는 질문/공지사항은 링크가 아닌 일반 li 텍스트다. 페이스북/유튜브는 href=#다. 도움말이나 채널처럼 보이지만 유효한 목적지로 이어지지 않는 항목을 정리한다.
- 사진 없는 지점은 192px 회색 영역을 유지하고, 지점 데이터 없음은 사용자에게 관리자 등록을 요청한다. 두 상태 모두 사용자 입장에서 행동 가능한 안내로 바꿀 필요가 있다.

### 권장 메인 구성

1. 실제 공간 사진 + 짧은 소개 + 지점 탐색 CTA. 모바일에서는 첫 화면의 제목/버튼/사진 비중을 조정한다.
2. 지점 비교 목록: 위치, 월간 공실, 실제 요금 정보, 상세 이동을 한 카드에 모은다. 고정 공실 카드는 본문 안으로 통합한다.
3. 확인된 시설·이용 장점만 간결하게 안내한다.
4. 이용절차는 압축된 4단계로 설명한다.
5. 유효한 문의/도움말 경로를 제공한다.

개선의 목표는 빈 공간을 장식으로 채우는 것이 아니라 첫 방문자가 원하는 지점과 방을 더 빨리 판단할 수 있게 하는 것이다. 이 절에서는 수정안을 구현하지 않았다.
